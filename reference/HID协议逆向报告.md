# DELUX M618XSD 鼠标驱动 HID 协议逆向报告

> 目标文件：`618XSD驱动文件.exe`（Inno Setup 6.1.0 安装包，产品名 "DELUX Office Driver"）
> 解包产物：`extracted\app\`；本报告基于静态反汇编（capstone + PE 解析），未运行任何安装程序。
> 分析日期：2026-07-31

## 0. 结论摘要

- 这不是内核驱动，而是纯用户态 HID 程序：`Mouse.exe` + `hiddriver_ms_*.dll` + `Hook.dll` + `hidapi.dll`。
- 设备通信 = HID **Feature Report**（特性报告），核心通道是 `SetFeature`（写入），响应经 Input Report 上行。
- 通信对象是 DELUX（多彩）**M618XSD** 鼠标（同套件还支持 M618Mini / M618Mini DB / M618AIR / M618XSC）。
- USB VID/PID：**0x1D57 / 0xFA60**（hidapi 枚举参数实际为 `_hid_enumerate(0x1D57, 0xFA60)`，已通过本机实测枚举确认）。
- 设备暴露两个 HID 接口：UsagePage **0x0B**（特性设备，收发配置）和 UsagePage **0x0A**（数据设备，输入报告/身份上报），Usage 均为 0。
- 实测（2026-07-31）：2.4G 接收器枚举为 "2.4G Wireless Device"，接口集合与上一条完全吻合；用 `hiddriver_ms_4.dll` 的 `Set_VIDPID(0x1D57, 0xFA60)` + `Open_FeatureDevice()` 成功打开特性接口，`0C` 初始化命令与 `06 09` DPI 命令均被固件接受（返回 1）。

## 1. hiddriver_ms_1.dll（80KB，x86，无壳）

### 1.1 导出函数（9 个）

| 导出 | 语义（已还原） |
|---|---|
| `Set_VIDPID(vid, pid)` | 保存过滤用 VID/PID（全局 0x1001415C/0x10014160） |
| `Open_DevMonitor(hwnd, param, msg)` | 启动隐藏窗口线程 + 枚举现有设备 + 注册 DBT 设备通知；设备增删通过 `PostMessage(hwnd, msg, 0/1, node_id)` 上报 |
| `Close_DevMonitor()` | 停线程、发 WM_CLOSE、清空设备链表 |
| `Open_FeatureDevice()` | 枚举并打开 UsagePage 0x0B 的特性设备，句柄存入全局（0x10014150） |
| `Close_FeatureDevice()` | CloseHandle 特性设备 |
| `SetFeature(buf, len)` / `GetFeature(buf, len)` | 直通 `HidD_SetFeature` / `HidD_GetFeature`，**首字节即 Report ID，不做任何封装** |
| `Hid_Read` / `Hid_Write` | hidapi 模板遗留的中断读写（链表匹配逻辑存在缺陷，Mouse.exe 未调用，可视为死代码） |

### 1.2 设备生命周期

1. `DllMain`（sub_100016F0）：分配设备链表头（环形双链表，锚点 0x1001411C），初始化临界区（0x10014130）。
2. `Open_DevMonitor`：创建隐藏窗口线程（窗口类名 `"Thread In DLL"`，sub_10001560），
   然后枚举 HID 设备（`SetupDiGetClassDevsA` + `SetupDiEnumDeviceInterfaces`），逐个尝试打开。
3. 打开逻辑 sub_10001D70：
   - `CreateFileA(path, GENERIC_READ|GENERIC_WRITE, SHARE_RW, OPEN_EXISTING, FILE_FLAG_OVERLAPPED)`
   - `HidD_GetPreparsedData` → `HidD_GetAttributes` → `HidP_GetCaps`
   - 过滤条件：**USB VID/PID == Set_VIDPID 的值**，且 `HIDP_CAPS.UsagePage == 0x0A`（数据设备）或 `0x0B`（特性设备）、`Usage == 0`
   - 数据设备命中：分配输入缓冲（InputReportByteLength）、`RegisterDeviceNotificationA`、创建读线程（sub_10001000，每 10ms 读一次）→ 打印 `"OpenHidDevice Success"`
   - 特性设备命中：句柄存入全局 0x10014150 → 打印 `"OpenFeatureDevice Success"`
4. 每个数据设备节点分配递增 ID（全局 0x10013000，从 1 起），并 `PostMessage(hwnd, msg, 1, node_id)` 通知"设备已添加"；节点插入链表。
5. 移除/挂起恢复：`WM_DEVICECHANGE`(0x219) / `WM_POWERBROADCAST`(0x218) 走窗口过程 sub_100010A0 / sub_10001260，按句柄匹配节点、卸载、`PostMessage(hwnd, msg, 0, node_id)`。

### 1.3 身份上报（Input Report ID 3）

读线程解析输入报告（sub_10001A70），当 `buf[0] == 3` 时：

```
VID = (buf[2] << 8) | buf[1]     ; 大端序
PID = (buf[4] << 8) | buf[3]
PostMessage(hwnd, msg, wParam=param, lParam=(PID << 16) | VID)
```

并缓存到全局 0x10014164/68。调试串：`InputReportBuffer:%x, %x, %x, %x, %x`。

> ⚠️ **2026-08-03 修订**：上面对 `buf[3]` 的"=PID 低字节"解读是**身份上报场景**的静态还原。
> 用户实机确认：**按鼠标 DPI 键切档时，同一 Input Report（ID=3）的 `buf[3]` = 当前档位（1-based, 1-8）**。
> 即 `buf[3]` 在不同上报场景下语义不同（身份首包=PID 低字节 / 切档事件=档位）。
> 上位机应以"切档时 buf[3]=档位"为准来同步 UI（见 3.4 节与 AGENTS.md 2.4 节）。

## 2. Mouse.exe 命令层

### 2.1 驱动加载

- 按型号 `LoadLibraryW("hiddriver_ms_N.dll")`（N=1..5 对应 M618Mini..M618XSC），再 `GetProcAddress` 7 个导出：

| 对象字段 | 导出 |
|---|---|
| +0x30 | Open_DevMonitor |
| +0x34 | Close_DevMonitor |
| +0x38 | Open_FeatureDevice |
| +0x3C | Close_FeatureDevice |
| +0x40 | SetFeature |
| +0x44 | GetFeature |
| +0x48 | Set_VIDPID |

- 启动序列（0x412000 初始化尾部）：
  `Set_VIDPID(vid, pid)` → `Open_DevMonitor(hwnd, 0x603, 0x604)` → `Open_FeatureDevice()` → `SetTimer(hwnd, 0x200, 6000ms)`。
- **备胎**：当 hiddriver 加载/打开失败时（标志 +0x404），改用 `hidapi.dll`：
  `_hid_enumerate(0x1D57, 0xFA60)` → 按 UsagePage 0x0B/0x0A 各打开一个设备 → 后台线程 `_hid_read`。

### 2.2 命令发送函数（0x417400）

签名：`SendCmd(this, cmd, len)`，`cmd[0]` 是 Report ID。

```c
if (cmd[0] != 0x09)
    hiddriver.SetFeature(cmd, len);          // 直通 HidD_SetFeature
else {
    // 拆成 3 个 64 字节特性报告（chunk 0..2），任意一个成功即停，失败重试：
    //   [0]=0x09 [1]=0x40 [2]=cmd[2] [3]=chunk_index [4..63]=cmd[3..] 分段载荷
    // 每块之间 Sleep(200ms)
}
// hidapi 备胎：
//   _hid_send_feature_report(dev, report, 0x40)，整批最多重试 10 次，每次 Sleep(500ms)
```

注意：0x09 命令的第 1 字节（如 0x83）在发送时被硬编码的 `0x40` 覆盖，即 `cmd[1]` 不参与线上协议（**例外**：chunk2 提交帧用 `0x0C` 而非 `0x40`，见 3.6 节）。

### 2.3 校验和

多数配置报告末尾带 **16 位累加校验和**（大端存储：高字节在前），覆盖范围从偏移 3（跳过 Report ID 和命令字）到校验和前一个字节。各报告偏移见下表。

### 3.2 灯光 + 电源管理配置（len=15，Report ID 0x05 / 0x0F）

> ✅ **2026-08-05～06 USBPcap 抓包差分验证**：全部字段功能已确认。
>
> ⚠️ **2026-08-07 实测结论：自定义命令设置电源不可靠。**
> 0x05 报告编码已确认（byte5=睡眠=`(分钟<<4)|8`，byte9=一级休眠=`分钟×2`，power_3/4/5 抓包验证），
> 但通过自定义命令发送 0x05 设置电源时，设备反应不稳定：有时生效、有时被忽略、有时触发异常行为
> （3分休眠导致深睡而非浅睡），甚至发生过 2.4G 断联（固件崩溃）。**建议电源管理通过官方软件操作**。

```
offset 内容
0      05
1      0F
2      01
3      灯光模式（低4位）+ 移动关灯（bit7）
        bits 0-3: 灯光模式（0=关闭, 1=呼吸DPI, 2=常亮DPI, 3=循环呼吸, 4=霓虹）
        bit 7: 移动关灯（0=开启, 1=关闭）
4      呼吸速度：byte4 = 9 - 速度值（范围 4-8，速度快慢由滑块控制）
5      睡眠时间：byte5 = (分钟 × 16) + 8，即 (sleep_minutes << 4) | 0x08（范围 1-60 分钟）
6      00（固定值）
7      00（固定值）
8      ff（固定值）
9      一级休眠时间：byte9 = 分钟 × 2（01=0.5min, 02=1min, …）
10     按键响应时间（去抖）：byte10 = 去抖值 ÷ 2（范围 1-25ms，默认 6ms→03）
11     校验和高字节
12     校验和低字节
13-14  00 00
```

**灯光模式映射（已验证）：**

| 模式名 | XML 编号 | byte3 低4位 |
|--------|---------|------------|
| 关闭 (LED Off) | mode 1 | 00 |
| 呼吸DPI (Breathing) | mode 2 | 01 |
| 常亮DPI (Solid) | mode 3 | 02 |
| 循环呼吸 (Cycle) | mode 4 | 03 |
| 霓虹 (Neon) | mode 5 | 04 |

公式：`byte3_low4 = mode - 1`。

**移动关灯：** byte3 的 bit7 = 0 表示开启（默认），bit7 = 1 表示关闭。

**呼吸速度：** byte4 = 9 - 速度值，速度范围 4（最慢）~ 8（最快）。默认值≈6（byte4=03）。

**睡眠时间：** byte5 = (分钟 × 16) + 8，范围 1~60 分钟。已验证：1分→0x18, 10分→0xA8, 15分→0xF8。

### 3.3 回报率设定（len=9，Report ID 0x06）

> ✅ **2026-08-05 USBPcap 抓包验证**：0x06 报告实际是**回报率（轮询率）命令**，此前误称为"DPI 选择"。

```
06 09 01  <idx>  <~idx>  00 00 00 00
```

- `idx` = 1000 ÷ 目标回报率（Hz）
- `~idx` = 0xFF - idx（按位取反）

**已验证的映射：**

| 回报率 | idx 值 | 补码 |
|-------|--------|------|
| 125 Hz | 08 | f7 |
| 250 Hz | 04 | fb |
| 500 Hz | 02 | fd |
| 1000 Hz | 01 | fe |

**例：** 设置 250Hz → `06 09 01 04 fb 00 00 00 00`

> ⚠️ 早期曾误认为 0x06 是"DPI 档选择"并单独发送，导致鼠标 OLED 显示 DPI=0、DPI 键失效（事故记录见 3.8 节）。实际原因是：该命令与 DPI 无关，单独发送会破坏设备内部状态。**正确用法是与 0x0C 唤醒配合发送，作为回报率设置命令。**

### 3.4 配置块 / DPI 配置（len=56，Report ID 0x04 / 0x38）

### 3.5 按键映射（len=59，Report ID 0x08 / 0x3B）

> ✅ 2026-08-01 通过抓包对比验证：18 个按钮 × 3 字节，支持宏绑定。
> ✅ 2026-08-01 用户实机逐键验证按钮编码与 UI→entry 映射（改键后按鼠标确认生效）。

```
08 3B 01  <每按钮 3 字节数据，按按钮索引 0..17 排列> ... <校验和16位>
```

- 每个按钮 3 字节数据：
  ```
  [0] 功能编码
       0x01=标准/未使用, 0x02=左键, 0x03=右键, 0x04=中键, 0x05=后退,
       0x06=前进, 0x09=上滚, 0x0A=下滚, 0x0B=左滚, 0x0C=右滚,
       0x0D=DPI循环, 0x12=宏
  [1] 参数 1（宏时=0x00，含义待定）
  [2] 参数 2（宏时=宏 ID，与 0x09 报告的宏 ID 对应）
  ```
- UI 按钮编号 → 协议 entry 索引映射：
  ```
  UI 1(左键)→entry[0]  UI 2(右键)→entry[1]  UI 3(中键)→entry[4]
  UI 4(前进)→entry[2]  UI 5(后退)→entry[3]  UI 6(DPI)→entry[5]
  UI 7(左滚)→entry[14] UI 8(右滚)→entry[15]
  UI 9(上滚)→entry[16] UI10(下滚)→entry[17]
  ```
- 默认 entry 表（来自官方软件抓包）：
  ```
  entry[0]=02 左键  entry[1]=03 右键  entry[2]=06 前进
  entry[3]=12 00 04 宏(后退)  entry[4]=04 中键  entry[5]=0D DPI循环
  entry[6..13]=01 未使用  entry[14]=0B 左滚  entry[15]=0C 右滚
  entry[16]=09 上滚  entry[17]=0A 下滚
  ```
- ⚠️ **风险提示**：0x08 为整表重写（18 个 entry 一次发出），未改的键须填设备真实默认值而非全 `01`，否则会清空设备原有按键表。
- 校验和：大端 16 位 = sum(报告[3..57])
- ⚠️ **整表覆写**：0x08 报告是整表重写（18 个 entry 一次发出），没有增量更新机制。
  2026-08-04 USBPcap 抓包确认：官方软件改一个键也是发完整 59 字节 0x08 报告，且在发送序列中**没有 GetFeature 读操作**。
  官方软件不改其他键是因为它在内存维护全部 18 个 entry 的副本，不是设备支持部分更新。
  自上写驱动必须维护本地配置，不能依赖"先读再改一个再写回"。

### 3.6 宏数据（len=131 → 线上 3×64，Report ID 0x09 / 0x83）

> ✅ **2026-08-02 实测验证通过**：前进键绑定宏 ID 1，按 G 键，播放方式 0x01 任意键停止，
> 按鼠标中键停止播放。
> ✅ **2026-08-07 实机验证**：三种播放方式全部实机打通（循环次数 1/5/8、任意键停止、按住循环），
> 延迟编码 500ms/1000ms 实机确认准确。

命令缓冲（0x83 字节）：

```
0       09
1       83（发送时被覆盖为 0x40，不参与线上协议）
2       宏 ID（与 0x08 entry 的 macro_id 对应）
3       播放方式（0x00=循环次数播放, 0x01=任意键停止播放, 0x02=按住循环）
4-6     动作值 ×3（通常为 0）
7       双重用途字节：
        播放方式为 0x00（循环次数播放）→ **循环次数值**（默认 1，macro_11 验证 5→0x05）
        播放方式为 0x01/0x02（任意键停止/按住循环）→ **修饰键**（bit0=LCtrl, bit1=LShift, bit2=LAlt, bit3=LGui）
        ⚠️ 官方用 0x01，之前误用 0x03 导致不生效
8-27    20 字节保留（全零）
28      按键对数量（按下+释放=2 对）
29      延迟模式标志
        0x01 = Default Delay 模式（未修改过默认值）
        0x03 = Default Delay 模式（默认值被修改过）
        0x07 = Record Delay 模式（原始录制格式，3 对含延迟信息）
30..    按键对，每对 2 字节：**[keycode, flag|delay]**（⚠️ 实测顺序！不是 [flag, keycode]）
        flag|delay: bit7=0x80按下/0x00释放, bits0-6=延迟编码值
        **编码公式（反汇编 0x004182B0 确认）：**
        - 延迟 ≤ 1270ms: `encoded = (int)(delay_ms / 100.0 + 0.5)`, 最小值为 1
        - 延迟 > 1270ms: `encoded = (int)((delay_ms % 200) / 100.0 + 0.5)`, 最小值为 1
        **示例：**
        - 10ms → 10/100+0.5=0.6→取整0→clamp1 → `0x81`（按下，延迟编码=1）
        - 100ms → 100/100+0.5=1.5→取整1 → `0x81`（按下，延迟编码=1）
        - 150ms → 150/100+0.5=2.0→取整2 → `0x82`（按下，延迟编码=2）
        - 1000ms → 1000/100+0.5=10.5→取整10 → `0x8A`（按下，延迟编码=10）
        - 2859ms → 2859%200=59→59/100+0.5=1.09→取整1 → `0x81`（按下，延迟编码=1）
        **注意：** 所有 < 50ms 的延迟都被编码为 1（最小值），
        无法区分 10ms 和 30ms。Record Delay 模式使用不同编码路径（见下）。
129-130 校验和（大端）= sum(cmd[3..129])
```

发送时拆分为 3 个特性报告：

```
chunk 0: 09 40 <macro_id> 00 <cmd[3..0x3E]>    (60 字节载荷)
chunk 1: 09 40 <macro_id> 01 <cmd[0x3F..0x7B]>  (60 字节载荷)
chunk 2: 09 0C <macro_id> 02 <cmd[0x7B..0x82] + 52×00>  ← ⚠️ 用 0x0C，不是 0x40
```

注意：chunk0 中 `09 40` 的 `40` 硬编码覆盖了 cmd[1] 的 `83`；**chunk2 官方用 `09 0C` 不是 `09 40`**（之前误以为是 hidapi 备胎差异，实测 0x40 会导致不生效）。

#### 播放方式与循环次数

| 方式 | internal[3] | internal[7] 含义 | 验证状态 |
|------|:---:|---|---|
| 循环次数播放 | 0x00 | **循环次数值**（默认1，已验证5→0x05） | ✅ 实机验证（2026-08-07） |
| 任意键停止播放 | 0x01 | **修饰键**（bit0=LCtrl, bit1=LShift, ...） | ✅ 实机验证（2026-08-02） |
| 按住循环 | 0x02 | **修饰键** | ✅ 实机验证（2026-08-07） |

**循环次数**：`internal[7]` 写入循环次数值（1-255）。0 会被 clamp 为 1（反汇编 0x0041832C 确认）。

#### Record Delay 模式 vs Default Delay 模式

| 特性 | Default Delay | Record Delay |
|------|--------------|-------------|
| `internal[29]` | 0x01（未改）或 0x03（改过） | 0x07（原始录制格式） |
| 按键对格式 | 标准 [keycode, flag\|delay] | 3 对含延迟信息的原始格式 |
| 编码方式 | `delay_ms ÷ 100 + 0.5` | 不同编码路径（值可比 Default 大很多） |
| 延迟写入鼠标 | ✅ 写入，<50ms 全编码为 1 | ✅ 写入，可记录真实间隔 |
| 延迟存储位置 | 协议 + 软件 macro.data | 协议（用于板载回放） |
| 经过测试的延迟值 | 10ms→1, 20ms→1, 30ms→1 | 582ms→0x39(57), 2859ms→0x07(原始) |

Record Delay 模式下，`internal[29]=0x07`，且按键对为 3 对（含额外延迟信息）。
应用阶段（apply）时，如果延迟值 ≤ 2550ms，会压缩为 `internal[29]=delay/10` 且按键减少为 2 对标准格式（如 macro_10 burst 2 的 582ms→0x39=57）。

### 3.7 官方"应用全部"序列（配置管理/Profile 机制）

> ✅ 2026-08-04 反汇编 0x00417B30 + 2026-08-06 USBPcap 抓包（profile_2.pcapng）双重确认。

官方软件点击"应用"或切换 Profile 时执行的完整序列（函数 0x00417B30）：

```
	0x0C 唤醒（10 字节，无条件）
	├─ [enable 0xf1]? → 0x04 DPI 配置（56 字节）
	├─ [enable 0xfb]? → 0x05 灯光+电源管理配置（15 字节）
	├─ [enable 0xf6]? → 0x06 回报率设定（9 字节）
	├─ [enable 0x100]? → 0x08 按键映射（59 字节）
	└─ 循环 18 个按钮：
	   └─ [entry[1]==0x11(宏) 且 enable 标志位为 1]?
	        → 0x09 宏数据（131 字节，调用 0x004182B0）
	```

**关键特点：**

1. **每个报告有独立的 enable 标志位**，只发被勾选的项。标志位在 `[esi+0xf1]`、`[esi+0xfb]`、`[esi+0xf6]`、`[esi+0x100]` 等。
2. **数据源是内存结构体 `[esi+0x5dbc0]`**，18 个按钮以 0x4F8 步长排列。
3. **各报告互不依赖**，写设备内存的不同区域。可以只发 0x08+0x09 改按键和宏，不影响 DPI 等。
4. **Profile 是纯软件层概念**，设备没有"配置"的概念。Profile 只是软件里存的一整套值，切换 Profile = 把整组值写入内存结构体然后触发"应用"循环。
   ✅ **2026-08-06 USBPcap 抓包验证（profile_2.pcapng）**：由日常配置切换至游戏配置时，官方软件发送了全套 8 条 SetFeature（0x0C→0x04→0x05→0x06→0x08→0x09×3），不存在"load profile N"命令。

**对上位机建议：**
- 本地维护一个 JSON 配置文件，包含所有功能的当前值
- 初始化用出厂默认值，改一个功能后更新 JSON 并发对应报告
- 不需要模拟完整的"应用全部"序列，按需发送即可

### 3.9 电池电量 + 充电状态 Input Report（5 字节，端点 0x83 IN）

> ✅ **2026-08-07 USBPcap 抓包分析 + 用户实机确认**：电池电量百分比和充电状态通过周期性 Input Report 从设备推送到主机。

鼠标在连接状态下（无线或有线）会通过 **接口 3 端点 0x83（IN）** 每 ~2 秒推送一个 5 字节的供应商状态报告：

```
03 28 40  XX  YY
```

| 偏移 | 值 | 含义 |
|------|----|------|
| 0 | `03` | 固定报告标识 |
| 1 | `28` | 固定头 |
| 2 | `40` | 固定头 |
| 3 | `XX` | **充电状态标志** |
| 4 | `YY` | **电池电量百分比（0-100 十进制）** |

**充电状态映射：**

| byte[3] 值 | 含义 | 出现场景 |
|:---:|------|----------|
| `01` | 未充电 / 满电（非充电态） | 无线使用中、电池充满 |
| `02` | 充电中 | 插线后电池正在充电 |
| `03` | 充电完成（满电挂线） | 电池已充满且仍插着线 |
| `04` | 插入检测 / 状态转换中 | 刚插上线时的初始上报 |

**证据表（两抓包交叉验证）：**

| 抓包 | 场景 | byte[3] 序列 | byte[4] 序列 | 电量 |
|------|------|:---:|:---:|:---:|
| 其他_10 | 插线充电（有线连接触发充电） | `04`→`02`→`03`（稳定） | `57`→`64`→`64`（稳定） | **87%→100%** ✅ 用户确认 |
| 其他_4 | 满电状态（电池 Input Report） | `01`（28 次全相同） | `63`（28 次全相同） | **99%** |

**读取路径说明：**

- **主要路径（设备→主机，推荐）**：端点 0x83 IN，设备主动推送，约 2 秒间隔。无需轮询，监听即可。
- **次要路径（主机→设备回显）**：端点 0x0A OUT，其他_4 抓包中主机向该端点写入相同格式数据（`03 28 40 01 63`），推测为官方驱动的回显/确认机制，非真实读取来源。

**对上位机的意义：**
- 无需 GetFeature 轮询，只需监听接口 3 端点 0x83 的 Input Report
- 解析 `[3]` 即可知晓充电状态，`[4]` 即实时电池百分比
- 该报告周期约 2 秒，不适合做精确的实时监控，但足够展示电池电量

## 5. 复现 / 替代实现建议

1. 用 `Set_VIDPID(0x1D57, 0xFA60)` 或直接枚举 VID/PID 找到设备；
2. 打开 UsagePage 0x0B、Usage 0 的特性接口；

   注意：**切 DPI 档位时，同一 Input Report 的 `buf[3]` = 当前档位（1-based）**，上位机应监听该上报同步 UI。
5. **宏写入核心流程**（已验证打通）：

   - modifier = 0x01
