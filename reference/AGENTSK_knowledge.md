## 0. 一句话结论

这"驱动"是**纯用户态 HID 程序**（无内核组件、无 .sys/.inf）。
与鼠标的通信 = **HID Feature Report 写入**（`HidD_SetFeature`，首字节即 Report ID）+ Input Report 身份上报。
目标设备：DELUX M618XSD（2.4G 无线接收器），**VID=0x1D57 PID=0xFA60**。

### ⚠️ 关键操作前置条件：必须关闭官方驱动

**向鼠标发送任何配置命令前，必须确保 `Mouse.exe`（官方驱动）已完全退出。** 官方软件运行时会持续抢占/覆盖设备配置，导致自写命令不生效甚至产生不可预期的结果（如 2.3 节事故记录）。最简单的确认方式：检查任务管理器或系统托盘确认无 `Mouse.exe` 进程残留。

### ⚠️ 电源管理额外前置条件：必须打开数据设备（0x0A）

**发送 0x05 报告中的电源字段（byte5 睡眠时间、byte9 一级休眠时间）前，必须先用 `Open_DevMonitor()` 打开数据设备（UsagePage 0x0A），否则设备忽略电源设置。**

原因是官方软件（Mouse.exe）的初始化序列为：
1. `Open_DevMonitor(hwnd, param, msg)` → 打开数据设备（0x0A）+ 创建隐藏窗口 + 启动读线程
2. `Open_FeatureDevice()` → 打开特性设备（0x0B）

而简单工具（如 `dpi_test.py` 这类早期脚本）只调用 `Open_FeatureDevice()`，从未打开数据设备，导致设备不接受电源设置。

**影响范围：** 灯光字段（byte3/4）、去抖（byte10）不受此限制，可单独发送 0x05 报告。只有电源字段（byte5/9）需要数据设备已打开。

**验证方法（2026-08-07 实机确认）：**
```python
user32 = ctypes.windll.user32
hwnd = user32.GetDesktopWindow()
dll.Open_DevMonitor(hwnd, 0, 0)  # 先开数据设备
time.sleep(1)
dll.Open_FeatureDevice()          # 再开特性设备
```

- ✅ 同一 iface=2 上暴露多个集合：

  - UsagePage **0x0B / Usage 0** → **特性设备（配置读写，核心接口）**

### 1.3 hiddriver DLL 语义（静态还原 + 部分实测）
- ✅ 导出 9 个：`Set_VIDPID(vid,pid)` / `Open_DevMonitor(hwnd,param,msg)` / `Close_DevMonitor()`
  / `Open_FeatureDevice()` / `Close_FeatureDevice()` / `SetFeature(buf,len)` / `GetFeature(buf,len)`
  / `Hid_Read` / `Hid_Write`。
- ✅ `SetFeature`/`GetFeature` 是 `HidD_SetFeature`/`HidD_GetFeature` 直通，**不封装、不加帧**，buf[0] 即 Report ID。
- ✅ 设备过滤：USB VID/PID == `Set_VIDPID` 值，且 `HIDP_CAPS.UsagePage==0x0A`（数据）或 `0x0B`（特性）、Usage==0。
  特性设备句柄存全局（DLL 内 0x10014150）。
- ✅ `Hid_Read`/`Hid_Write` 是 hidapi 模板遗留，**Mouse.exe 从不调用**（可忽略/当作死代码）。
- ✅ 身份上报：Input Report ID **3**，`buf[1..2]`=VID（大端）、`buf[3..4]`=PID（大端），
  经 `PostMessage(hwnd, msg, wParam, lParam=(PID<<16)|VID)` 通知宿主。
- ✅ 热插拔：隐藏窗口类名 `"Thread In DLL"`，`Open_DevMonitor` 消息参数为 (hwnd, 0x603, 0x604)，
  设备节点 ID 从 1 递增。

> 0x05 实为灯光+电源管理配置，0x06 实为回报率命令（详见 HID协议逆向报告.md 3.2/3.3 节）。

### 2.3 事故记录（2026-07-31）

- 单独发送 `06 09 01 01 FE 00 00 00 00`（未配合其他报告）导致鼠标 OLED 显示 DPI=0、DPI 键失效、开关机无效；由官方软件恢复。
- 教训：**在协议字节验证前禁止向设备盲发配置命令**；字段定位一律用"官方软件操作 + 只读快照差分"或抓包。

### 2.3b 事故记录（2026-08-01，自写上位机 0x08 按键）

- 通过上位机程序的「应用按键」发送 `0x08` 报告（`08 3B 01 <18×3字节> 校验和`），
  试图把左滚改为中键 → **鼠标所有按键失效**（报告中除尾部一个 `04 00 00` 外，其余按钮全为 `01 00 00`，
  即文档定义的 0x01=标准/未使用，等于把整张按键表禁用）。禁用档位、激活档位均同时失效。由官方 `Mouse.exe` 恢复。
- **根因**：0x08 的按钮编码与「UI 编号→协议 entry 索引」映射（AGENTS.md 6 节）当时是 ⚠️ 推断值，不可靠；
  且默认把所有未配置的按钮填成 `01`（未使用），一旦整体写入即清空设备按键表。
- **后续**：用户在 2026-08-01 用 Python + 官方 `hiddriver_ms_4.dll` **实机逐键验证了** 0x08 的按钮编码与
  entry 映射（改键后实机按鼠标确认生效），协议状态据此在 6 节升级为 ✅。详见 6 节。
- 教训：凡 AGENTS.md 标 ⚠️/❓ 的 Report，其字段都属"能发但不准"，写入即可能破坏设备配置；
  但**用户实机手动验证的字段可升级为 ✅**，比单纯静态推断/抓包更可靠。

### 2.3c 事故记录（2026-08-07，0x05 电源管理测试导致断联）

- 发送 `0x05` 报告（从官方抓包 `power_4` 复制的精确字节，byte9=0x04=2分一级休眠）后，**2.4G 无线信号断联**，
  鼠标完全无响应。由拔插接收器/重启鼠标恢复。
- **根因（2026-08-07 后期定位）**：**未打开数据设备（0x0A）就发送电源命令。** 官方软件初始化序列为
  `Open_DevMonitor()`（开数据设备）→ `Open_FeatureDevice()`（开特性设备），而简单工具只调用了
  `Open_FeatureDevice()`。设备在数据设备未打开时，可能处于"半唤醒"状态，接收到电源 Feature Report 后崩溃。
- **教训**：电源管理命令（0x05 byte5/9）必须先打开数据设备（0x0A），否则不可靠甚至导致断联。
  - 有时生效（1分休眠在特定条件下触发过）
  - 有时不生效（2分、3分休眠设置被忽略，设备使用默认值）
  - 有时触发异常行为（3分休眠导致深睡而非浅睡）
  - 有时导致固件崩溃/断联（本次）
- **教训**：电源管理协议（0x05 报告）的字段编码虽然已厘清，但**设备对自定义命令的电源设置反应不稳定，有断联风险**。
  建议电源管理仍通过官方软件（Mouse.exe）操作。后续如需继续研究，应先搞清楚设备的状态管理机制（如前置条件、时序要求）。

### 2.3d 事故记录（2026-08-09，0x08 与 0x09 之间缺 0.2s 间隔导致宏不落盘）

- 现象：0x0C→0x08→0x09×3 三帧字节经核对全部正确、WriteFeature 全部返回 OK，但绑宏的按键（后退键 entry[3]）按下仍执行原功能（后退），宏未生效。
- **根因**：自写上位机 `ApplyButton()` 在 `Send(BtnCfg.ToBytes())`（0x08 整表覆写）之后**直接** `SendMacroDataIfAny()`（0x09×3），二者之间**没有 0.2s 间隔**。官方时序要求每步间隔 0.2s（见 8 节），固件刚接收完 0x08 还没消化就被 0x09 宏数据打断，宏数据未真正落盘（或 0x08 整表覆写被后续 0x09 流打断未稳定应用）。
- **修复**：在 `Send(BtnCfg.ToBytes())` 与 `SendMacroDataIfAny()` 之间补 `Thread.Sleep(200)`（0x09×3 每块间原本已有 0.2s），完整时序 = `0x0C`→sleep(0.2)→`0x08`→sleep(0.2)→`0x09×3`（每块 sleep(0.2)）。补后实机验证：后退键绑宏 ID 3 生效，按后退键触发宏（发 B 键）。
- **教训**：协议文档"每步间隔 0.2s"不仅指 `0x0C→0x08`，**`0x08→0x09` 之间也必须间隔 0.2s**，否则宏不落盘。字节正确 + WriteFeature 返回 OK ≠ 固件真正接受，时序是独立约束。

### 2.4 DPI 协议

- 0x04 报告（56 字节）**写入**成功，OLED 生效（✅ 写入侧）。`[24]`=目标档位索引（1-indexed），写入即切档。
- 校验和：`sum(报告[3..49]) & 0xFFFF`，大端。
- ✅ **档位读取的两类情形（已厘清）**：
  - ❌ **主动读取不可行**：连接后 GetFeature(0x04) 的 `[24]` 恒为 0、回读是命令回显而非真值，无法"查询"鼠标当前在第几档（2026-08-02 实机证伪）。
  - ✅ **硬件切档上报可读**：按鼠标 DPI 键切档时，Input Report（ID=3）的 `buf[3]` = 当前档位（1-based, 1-8，用户实机确认）。旧文档称 `buf[3]=PID`（HID协议逆向报告.md 1.3 节）应是误判或仅身份上报首包如此；**切档场景下以 `buf[3]=档位` 为准**。
  - 上位机做法：软件切档写 0x04 `[24]` + 本地记忆 `_currentLevel`；并监听 Input Report，`OnDpiLevelChanged` 收到硬件切档上报即同步 UI 高亮与本地记忆（双向一致）。
  - **已落地到 `MouseDriverClient`**：`_currentLevel` 本地记忆；「应用 DPI」（0x04 写档位+全套数值）、「切档」（0x0C→0x04 仅改 `[24]`，轻量可频点）；Input Report 监听恢复为驱动 UI 高亮（硬件切档自动跟随）。详见 `MouseDriverClient/MouseDriverClient状态记录.md` 2 节。
- GetFeature 按 Report ID 寻址、可反复读；⚠️ Report ID 不可为 0（Win32 错误 87）。能读 ≠ 读出来是真值。

- 使用方法：双击 → 选功能 → 填备注 → 点「开始抓包」→ UAC 确认 → 操作官方软件 → 点「停止抓包」

- ✅ **DPI 写入切档**（0x04 写 `[24]` 即切档，OLED 生效）；❌ 当前档位不可读，上位机用"写入+本地记忆"。
- ✅ **按键映射（0x08）**（2026-08-01 用户实机验证，详见 HID协议逆向报告.md 3.5 节）
  - ⚠️ **0x08 是整表覆写**，没有增量更新机制（2026-08-04 USBPcap 抓包确认：官方软件改一个键也是发完整 59 字节 0x08 报告，没有 GetFeature 读操作）
  - 官方软件不改其他键是因为它在内存维护全部 18 个 entry 的副本，不是设备支持部分更新
  - **"先读后写"方案不可行**：设备不支持读按键表。正确做法是上位机本地维护配置文件（JSON/INI），初始化用出厂默认值，改一个 entry 后整表写出
- ✅ **宏协议（0x09）**（2026-08-02 实测打通，详见 HID协议逆向报告.md 3.6 节）
  - ✅ **宏 ID 覆盖写入**（2026-08-07 实机确认）：同一宏 ID 可反复覆盖（播放方式/循环次数/按键序列均可改），无需每次都换新 ID
- ✅ **轻量序列（0x0C+0x08+0x09×3）可用且不断连**（2026-08-04 用户实机确认：同一命令 `macro_write_simple.py --btn 8 --key P`、未先恢复配置、Mouse.exe 完全退出态下跑通，右滚→P 生效、不断连、DPI 不变）。**关键前提：发送前 Mouse.exe 必须完全退出**——断联的真正主因是官方驱动抢占，而非缺 0x04/0x05/0x06 前置报告。此前「必断联」结论（2026-08-02）为误诊，已作废。
- ✅ **灯光协议（0x05 byte3/byte4）**（2026-08-05 USBPcap 抓包确认）：byte3 低4位=灯光模式(0-4)，bit7=移动关灯(0=开启/1=关闭)；byte4=9-速度值(范围4-8)。
- ✅ **回报率协议（0x06）**（2026-08-05 USBPcap 抓包确认）：idx = 1000 ÷ Hz（125Hz→08, 250Hz→04, 500Hz→02, 1000Hz→01）。
- ✅ **电源管理-一级休眠（0x05 byte9）根因已定位（2026-08-08，反汇编确认）**：
  - **偏移本质**：固件把 byte9 当 **1-based 的 0.5 分档计数**，实际分钟 = `(byte9 - 1) × 0.5`；
    PC 端（含官方 Mouse.exe）编码约定为 `byte9 = 分钟 × 2`，两者 off-by-one → **每档系统性 -0.5 分**。
  - **反汇编证据**（mouse_analysis3.txt → 函数 0x417E60，约第 108-115 行）：
    ```asm
    mov  dl, byte ptr [edi + 0x95d]   ; byte9 来源（一级休眠，来自配置结构体）
    mov  byte ptr [ebp - 0x61], dl    ; 原样直写报告，无 ×2 / -1 运算
    ```
    byte9 由发送端原样透传，偏移**不在发送端**，纯属固件解码端的固有行为。
  - **现象印证**：用户实机确认——用官方软件设 2 分，实际 ≈1.5 分熄灭（同样偏移），证明与自写命令无关，是固件固有。
  - 官方抓包映射表（即 `分钟×2`，无 +1）：0.5→01, 1→02, 1.5→03, 2→04, 3→06, 3.5→07
    —— 代入 `(byte9-1)×0.5` 全部完美吻合「标称 -0.5 分」线性规律。
  - **修正公式（已落地 power_send.py）**：`byte9 = round(分钟×2) + 1`（无条件 +1），
    使 `实际 = (byte9-1)×0.5 = (分钟×2+1-1)×0.5 = 分钟`，消除偏移。
  - ⚠️ 仍受 §0 前置条件约束：**需先 `Open_DevMonitor()` 打开数据设备(0x0A) 才生效**，否则被忽略/断联。
- ⚠️ **电源管理-睡眠时间（0x05 byte5）**：编码已抓包确认 byte5 = (分钟×16)+8，同需数据设备(0x0A)前置。
- ℹ️ **电源管理操作要点（2026-08-07 实机总结）**：
  1. 必须关闭 Mouse.exe
  2. 必须先用 `Open_DevMonitor()` 打开数据设备(0x0A)
  3. 再 `Open_FeatureDevice()` 打开特性设备
  4. 发送 0x0C 唤醒 → 等 1秒 → 发送 0x05 报告
  5. byte9 公式需用修正版（round(分钟×2)+1，无条件 +1，详见一级休眠条目根因）
- ✅ **宏延迟编码（完整厘清，2026-08-09 实测修正）**：
  - **PC 端编码公式（反汇编 0x004182B0 确认）**：`encoded = max(1, int(delay_ms / 100.0 + 0.5))`；`> 1270ms` 时 `(delay_ms % 200) / 100 + 0.5`。所有 `< 150ms` 的输入（0-149ms）都编码为 byte 1。
  - **⚠️ 设备端解码公式（2026-08-09 实测，推翻早期"500ms/1000ms 准确"结论）**：
    ```
    实际动作延迟 = max(10ms, 编码byte × 5ms)
    ```
    实测四档全部拟合：byte1→10ms, byte2→10ms, byte5→25ms, byte10→50ms。
    **注意：设备端解码是 byte×5ms，不是 byte×100ms。** 早期文档里"500ms/1000ms 延迟验证准确"验证的是 **PC 端编码**（500ms→byte5 正确），而非设备端实际延迟。
  - **有效映射表（UI 想设的延迟 → 设备实际延迟）**：
    | 设备实际延迟 | UI 输入 | 编码 byte | 设备端 |
    |---|---|---|---|
    | 10ms（最小） | 10ms（0-100ms 均可） | 1 | 10ms |
    | 25ms | 500ms | 5 | 25ms |
    | 50ms | 1000ms | 10 | 50ms |
    | 100ms | 2000ms | 20 | 100ms |
    | 500ms | 10000ms | 100 | 500ms |
  - Record Delay 模式使用不同编码路径，`internal[29]=0x07`，延迟值可更大（如 582ms→0x39=57）。详见 HID协议逆向报告.md 3.6 节。
  - **结论影响**：UI 上的"延迟(ms)"输入框标注的是 PC 端编码输入值，设备实际生效延迟需按上表换算（约 UI值 ÷ 20）。若需更精细延迟，受 byte×5ms 量化限制，最小分辨率 5ms、最小 10ms。
  - **上位机实现（2026-08-09 实际落地）**：`Models.cs` 提供 `PcInputToActualMs`（PC 端输入→设备实际生效延迟，只读换算）；`MacroEditor` 的延迟输入框按「PC 端延迟(ms)」原样存入 `MacroAction.DelayMs`（不做换算），列表与编辑/插入回执中只读展示「设备实际≈Xms」，消除「填1000实际50」误解。
- ✅ **播放方式 0x00 循环次数**（2026-08-07 实机验证：循环次数 1/5/8 全部确认）：`internal[7]` 存循环次数值，循环次数默认 1，0 被 clamp 为 1。
- ✅ **播放方式 0x02 按住循环**（2026-08-07 实机验证）：按住前进键时持续输出，松开停止。三种播放方式全部打通。
- ✅ **按键响应时间-去抖（0x05 byte10）**（2026-08-06 USBPcap 抓包确认）：byte10 = 去抖值 ÷ 2，范围 1-25ms。已验证：6ms→03, 10ms→05。
- ❓ **灯光亮度**：在 0x05 报告中的字节位置待确认——当前 bytes 6-8 在多次抓包中值固定（00 00 ff），需单独抓包验证。
- ✅ **电池电量 + 充电状态协议**（2026-08-07 USBPcap 抓包分析 + 用户实机确认 87%）：
  - 周期性 Input Report（~2 秒）：`03 28 40 XX YY`，端点 0x83 IN（设备→主机）
  - `byte[3]` = 充电状态：`01`=未充电/满电, `02`=充电中, `03`=充电完成, `04`=插入检测
  - `byte[4]` = 电池电量百分比（0-100 十进制直读）
  - 验证：其他_10（插线 87%→100%）；其他_4（满电 99%）
  - 详见 HID协议逆向报告.md 3.9 节

## 7. 配置管理（Profile）机制

### 7.1 本质

**配置管理（Profile）是纯软件层功能，设备本身没有"配置"概念。** 设备只有扁平的内存页，每个 Report ID 写不同区域。Profile 只是软件里存的一整套值，切换 Profile 就是把整组值写入内存结构体然后触发"应用"循环。

✅ **2026-08-06 USBPcap 抓包验证（`profile_2.pcapng`）**：由日常配置切换至游戏配置时，官方软件向设备发送了**全套 8 条 SetFeature**（0x0C 唤醒 → 0x04 DPI → 0x05 灯光+电源 → 0x06 回报率 → 0x08 按键映射 → 0x09×3 宏数据），**不存在"load profile N"或"切换到槽位 N"的短命令**。切换 Profile 等价于把另一组预设值逐条写入设备。这与"应用全部"流程（7.2 节）本质相同，仅是数据源不同。

### 7.2 官方"应用全部"流程（反汇编 0x00417B30）

```
	0x0C 唤醒（无条件）
	├─ [enable_0xf1]? → 0x04 DPI 配置（56 字节）
	├─ [enable_0xfb]? → 0x05 灯光+电源管理配置（15 字节）
	├─ [enable_0xf6]? → 0x06 回报率设定（9 字节）
	├─ [enable_0x100]? → 0x08 按键映射（59 字节）
	└─ 循环 18 按钮：
	   └─ [entry+1]==0x11(宏) 且 [enable_0x109+idx]==1?
	        → 0x09 宏数据（131 字节）
	```

- 每个报告有独立的 enable 标志位，只发被勾选的
- 数据源：`[esi+0x5dbc0]` 内存结构体（18 按钮 × 0x4F8 步长）

### 7.3 各报告的独立性

| 报告 | 功能 | 独立发送？ |
|------|------|-----------|
| 0x04 | DPI 数值 | ✅ 可单独发，不影响其他 |
| 0x05 | 灯光+电源管理 | ✅ 可单独发 |
| 0x06 | 回报率设定 | ✅ 可单独发 |
| 0x08 | 按键映射 | ✅ 可单独发（+0x0C 唤醒） |
| 0x09 | 宏数据 | ✅ 可单独发（+0x08 绑定） |

各报告写设备内存的不同区域，互不干扰。**上位机可以只发需要的报告，不用管其他的。**

### 7.4 对上位机的意义

- 本地维护一个 JSON 配置文件，包含所有功能的当前值
- 初始化用出厂默认值
- 改一个功能 → 更新 JSON → 发对应报告
- 各报告独立，可以只发 0x08+0x09 改按键和宏，不管 DPI/灯光

## 8. 宏写入核心流程

详见 `HID协议逆向报告.md` 3.5 节（0x08 按键映射）和 3.6 节（0x09 宏数据）。

**一句话流程：** 0x0C 唤醒 → 0x08 按键映射 → 0x09×3 宏数据（**每步之间都间隔 0.2s**，含 0x08→0x09 这步，见 2.3d 事故）。轻量序列，不会断连——**前提是 Mouse.exe 已完全退出**（2026-08-04 实机确认；断联案例根因均为官方驱动未退出抢占，非序列本身）。
**关键陷阱：** modifier=0x01、chunk2 用 0x0C、按键顺序为 [keycode, flag|delay]。

- ✅ 已还原命令中**没有**出厂重置/固件写入类指令；向自有设备发送配置报告风险低（最坏被忽略）。
- ⚠️ 校验和/字段未确认前，灯光与按键命令一次只改一个变量，便于定位。
- ✅ ctypes 加载 DLL 不安装任何东西、不改系统注册表；脚本进程退出即释放。
- ℹ️ 2.4G 接收器对 PC 是标准 USB HID 设备，抓包即可看到全部配置流量；BLE 模式才需要 BLE sniffer。
